## 1. 设计原则

1. **运行区只读运行，构建区独立构建**：运行中的 checkout 绝不在构建期间被改动；新版本在独立的 git worktree 中构建，替换前前台零感知。
2. **git fetch 不碰工作树**：检测更新只 `git fetch`（更新远程引用），运行区工作树保持原样。
3. **原子替换 + 可回滚**：目录替换用"旧→备份、新→运行位"两步 + 失败回滚，保证任意时刻至少有一个可用版本。
4. **壳层注入，零前端改动**：就绪提示条由 preload 注入（延续沉浸式迭代的原则）。
5. **状态机串行**：升级状态（idle→checking→building→ready→applying→applied→failed）单例串行，并发触发被拒绝。

## 2. 目录与文件布局

```
.app/Contents/Resources/harness-bundle/   ← 打包内置（构建好的 checkout：源码+node_modules+lib+dist+.git）
~/dsh-app/
├── harness/          ← 运行区（首次从 bundle 解包；带 .git；只读运行）
├── harness-new/      ← 构建区（git worktree；构建完成后待替换）
├── harness-old/      ← 备份区（替换时旧版暂存，成功后删除）
├── update-state.json ← 升级状态机持久化（跨崩溃恢复）
├── settings.json     ← 既有配置（新增字段见 §7）
├── env / logs/       ← 既有
```

- 运行区带 `.git`：首次解包后由 bundle 携带完整 `.git`（内置时随包复制），确保 `git fetch`/`worktree` 立即可用，**首次打开不执行任何 git**。
- `update-state.json` 结构：
```json
{
  "state": "idle|checking|building|ready|applying|applied|failed",
  "fromCommit": "…", "toCommit": "…", "tag": "…",
  "buildError": "", "startedAt": 0, "finishedAt": 0
}
```

## 3. 打包内置（构建侧）

1. `scripts/bundle-harness.sh`：从参考 checkout（已 `pnpm build` 完成）复制到 `build/harness-bundle/`：
   - 全部源码 + `.git` + `node_modules` + `apps/web/dist` 等构建产物（全量策略，见决策点 1）
   - 排除：`*.tsbuildinfo`、测试产物等非必需（可后续优化）
2. `electron-builder.yml` 增加 `extraResources: [{ from: build/harness-bundle, to: harness-bundle }]`（不进 asar，原样复制）。
3. 打包时长：node_modules 文件数多，首次打包较慢（预期 3–8 分钟），可接受。

## 4. 首次启动（解包）

```
主进程启动 → 运行区不存在？
  ├─ 是：打开进度窗口("首次安装，解包内置版本…")
  │      fs.cp(bundle, ~/dsh-app/harness, { recursive })   // 本地复制 1–2 分钟
  │      → 启动后端（无 git）
  └─ 否：直接启动后端
```

- 若 `~/dsh-app/harness` 存在但损坏（缺 `apps/cli/lib/bin.js`）：提示用户删除后重试（保留现有语义）。
- 解包失败：删除半成品目录，报错退出，可重试。

## 5. 后台检测与构建

### 5.1 调度
- 启动后 20s 首次自动检测；之后每 6h；菜单"立即检查更新"手动触发（替换现有 ⌘U 行为）。
- 调度器只在 `state === 'idle'` 时启动新检测；构建中/就绪中忽略新触发。

### 5.2 检测（checking，纯 fetch）
```
git -C harness fetch origin --tags --prune        // 不碰工作树
tag 通道：latest = git tag --sort=-v:refname 取最新 dsh-v*
master 通道：origin/master
toCommit = rev-parse <target>^{commit}
fromCommit = rev-parse HEAD（运行区当前）
from === to → idle（静默）
有更新 → 进入 building
```

### 5.3 构建（building，后台，前台无感）

构建区用 **`git archive` 导出**（普通目录，无 `.git`），避开 worktree 在目录替换时 `.git` gitdir 文件断裂的问题：

```
rm -rf harness-new && mkdir -p harness-new
git -C harness archive <toCommit> | tar -x -C harness-new     // 导出 toCommit 快照（秒级）
pnpm install（CI=true；--frozen-lockfile 失败降级 plain，cwd=harness-new）
pnpm build（lib + web，cwd=harness-new）
  ├─ 任一失败 → 清理 harness-new → failed（记录 buildError，提示可重试）
  └─ 成功 → state=ready，写入 tag/commit，前台推送"新版本已就绪"
```

- 构建全程不触碰运行区；后端继续跑旧版本。
- 磁盘占用：构建区安装期间额外 ~1.2G（全量策略），替换后旧区清理回收。

### 5.4 就绪提示（ready → 前台）
- 主进程向渲染层推送 `dsh:update-event { state:'ready', tag, fromCommit, toCommit }`。
- preload 注入的提示条（右下角浮条）显示："新版本 vX 已就绪" + [立即更新] [忽略]。
- 忽略：提示条关闭，state 保持 ready（下次检测如版本未变不再重复提示）。
- "关于"面板同步显示构建状态。

## 6. 替换与重启（applying → applied）

用户点击"立即更新"（决策：**手动确认重启**）：
```
1. 校验：运行区工作树必须干净（dirty 则提示用户先处理，拒绝替换）
2. stopBackend()（约 1s 闪断）
3. 原子替换：
   rm -rf harness-old
   mv harness harness-old
   mv harness-new harness
   验证 harness/apps/cli/lib/bin.js 存在
     ├─ 失败 → mv harness-old harness（回滚）→ 提示失败，保持旧版可用
     └─ 成功 →
        mv harness-old/.git harness/.git          // 旧仓库 .git 迁入新运行区
        git -C harness reset --hard <toCommit>    // HEAD 对齐新版本（untracked 构建产物保留）
        rm -rf harness-old                        // 清理备份
4. state=applied
5. 启动新版后端 + 刷新窗口（GUI 立即为新版本，不中断使用）
6. 弹窗："新版本 vX 已生效，建议重启应用以获得最佳状态" → [立即重启] [稍后]
   - 立即重启：app.relaunch() + app.quit()（走优雅退出，后端 SIGTERM）
   - 稍后：继续使用（新版本已在运行）
```

- **"手动确认重启"语义**：替换完成后 GUI 不中断（后端重启 ≈1s），弹窗提醒可完整重启应用；用户点"立即重启"才执行 relaunch。
- 替换期间若崩溃：`update-state.json` 为 applying，下次启动检测到 `harness-old` 存在且 `harness` 缺失 → 自动回滚。
```

- 用户选择"重启生效"（决策点 4）：
  - A（自动）：替换后直接重启后端并刷新窗口，等效生效，弹窗仅告知。
  - B（手动确认）：替换后停在后端已按新版启动、窗口已刷新，弹窗让用户确认"重启应用"（app.relaunch）以获得最干净状态。
- 替换期间若崩溃：`update-state.json` 为 applying，下次启动检测到 `harness-old` 存在且 `harness` 缺失 → 自动回滚。

## 7. 配置（settings.json 新增）

| 字段 | 默认 | 说明 |
|---|---|---|
| `autoCheck` | `true` | 启动后后台自动检测（原默认 false，本轮改为 true） |
| `autoCheckIntervalMs` | `6 * 3600_000` | 自动检测间隔 |
| `channel` | `tag` | 沿用：tag / master |
| `updatePrompt` | `toast` | 就绪提示形式（toast 浮条） |

## 9. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 内置体积大（全量 1.2G+） | .app ≈1.5G、zip 大、打包慢 | 决策点 1 确认；后续可裁剪为 prod-only（增量优化，不在本轮） |
| 首次解包 1–2 分钟 | 首次打开等待 | 进度窗口 + 本地复制（非网络）；可后续做 tar 归档加速 |
| worktree 残留/冲突 | 构建失败 | worktree prune + 失败清理；状态机保证串行 |
| 替换瞬间后端/文件锁 | 替换失败 | 后端先停再换；旧→备份、新→运行位；失败回滚；崩溃恢复基于 update-state.json |
| 前后台双 node_modules 磁盘 | 峰值 ~2.4G | 替换后清理 harness-old；体积优化留后续 |
| 提示条与 GUI 视觉冲突 | 体验 | 右下角非模态浮条，可忽略，样式轻量 |
| 检测/构建与手动操作并发 | 状态错乱 | 状态机单例串行 + 单实例锁 |
| 断网/构建失败 | 无法升级 | 静默重试/提示可重试，旧版始终可用 |

## 10. 测试计划

1. 单元（Node 直接驱动 `upgrade.js`）：状态机流转、worktree 构建、替换回滚（在隔离 clone 上，复用 `.bootstrap-test/` 方法）。
2. 冒烟（`scripts/smoke.sh`）：首次解包路径、正常启动、`SMOKE_OK`、退出无孤儿。
3. 集成（隔离环境模拟）：
   - 后台检测到更新 → 构建区构建 → ready → 提示事件
   - 替换 → 重启 → 新版本生效；模拟替换失败 → 回滚
   - 断网检测 → 静默；构建失败 → failed 可重试
4. 手工验收清单（真实桌面）：
   - [ ] 删除 ~/dsh-app 后首次打开：解包进度 → 直接可用（无 git）
   - [ ] 后台自动构建期间 GUI 正常使用
   - [ ] 就绪提示条出现 → 忽略/更新均正常
   - [ ] 点击更新 → 替换 → 重启 → 新版本生效
   - [ ] ⌘U/重启后端/关于/日志回归
5. 回归：沉浸式窗口（红绿灯/拖拽区）不受影响。
