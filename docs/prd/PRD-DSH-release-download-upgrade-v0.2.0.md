## 1. 背景与目标

### 1.1 背景

当前升级管线为**源码构建式**（已实施）：应用后台 `git fetch` → `git archive` 导出快照 → 本地 `pnpm install` + `pnpm build` → 就绪提示 → 原子替换 → 重启生效。

该方案的固有成本：

| 痛点 | 说明 |
|------|------|
| 每台设备都要构建环境 | git、node ≥22、pnpm ≥11 需逐台发现与版本校验（壳层 §6.5 跨设备依赖发现）；缺一个就无法升级 |
| 每次升级重复构建 | 每台设备每次 install + build 数分钟，耗时随设备性能浮动 |
| 失败面大且不可控 | 设备环境差异放大构建失败率（既有 K-8 / K-14 等坑位均源于"在用户机构建"） |
| 产物不一致 | 每台设备各自构建，理论上可得到不同产物 |

**新方案（本 PRD）：产物下载式**。发布者在本地完成打包（构建环境可控、可预冒烟），将打包产物 + 更新清单上传到 GitHub Releases；应用检测到新版本后**下载打包产物**（而非源码）完成升级。构建从"每台用户设备反复执行"收敛为"发布者本地一次"。

### 1.2 目标

| 目标 | 说明 | 成功标志 |
|------|------|----------|
| 产物化发布 | 发布者本地一键打包 tar.gz + 更新清单，上传 GitHub Releases | 一次打包，所有设备拿到同一份已验证产物 |
| 下载式升级 | app 检测 Releases 新版本 → 后台下载 → 校验解压 → 就绪提示 → 替换重启 | 升级全程不打断前台使用 |
| 构建零依赖 | 用户端升级不再需要 node/pnpm/git 构建链 | 升级仅依赖网络与磁盘 |
| 保留源码通道 | 源码构建式升级**完整保留**，作为可选通道 | 通道可切换，两种方式均可升级 |
| 多架构/跨平台预留 | 本期只发布 macOS x64，但协议层（清单/命名/匹配）按多平台设计 | 后续加 Windows/Linux/arm64 时，设备端与协议零改动 |

### 1.3 非目标（本版本不做）

- Windows / Linux 打包目标与 Apple Silicon arm64 原生构建（**后续版本**；协议与架构预留见技术文档 §13，本期仅落地协议层）
- 壳二进制自更新（整个 .app 的替换，另立专项）
- 差分 / 增量更新（先全量下载，体积优化留后续版本）
- 代码签名与公证（个人自用沿用未签名；分发扩大后另立专项）

## 2. 目标用户与使用场景

| 用户 | 诉求 | 关键场景 |
|------|------|----------|
| **发布者**（开发者本人） | 一次打包、全员同产物 | 本地跑发布脚本 → 产物 + 清单上传 Releases；设备零操作 |
| **深度使用者** | 升级快、不打断使用 | 后台自动下载新版，就绪后右下角提示，一键更新 |
| **构建环境不全的设备** | 无法满足 node/pnpm 要求也能升级 | 升级不再需要任何构建工具链 |
| **开发者（追新）** | 想跟 master 最新源码 | 设置里切回源码构建通道 |

典型场景：

1. **场景 A：发布新版** — 发布者打 `dsh-v0.2.0` tag → 本地打包 tar.gz + 生成清单 → 上传 GitHub Releases。
2. **场景 B：自动升级（主通道）** — 应用后台发现 Releases 有新版本 → 静默下载 → 校验 → 解压 → 右下角提示"新版本 vX 已就绪" → 点更新 → 替换 → 重启生效。
3. **场景 C：下载异常** — 断网 / 哈希不符 / 产物损坏 → 清理重试，旧版始终可用，前台无感。
4. **场景 D：切回源码通道** — 用户在设置切 `source` 通道，走既有 git + 本地构建升级。

## 3. 升级状态机（用户视角）

```
[空闲] --启动后20s/每6h/手动检查--> [检测中](后台, 前台无感)
   ├─ 无新版本 ──────────────────────────────> [空闲]（静默）
   └─ 有新版本 --> [下载中](后台, 前台无感, 进度可在"关于"查看)
        ├─ 下载失败/哈希不符/解压失败 --> [失败](提示可重试) --> [空闲]
        └─ 下载+解压成功 --> [就绪]（前台提示"新版本 vX 已就绪"）
             ├─ 用户忽略 --> [空闲]（下次检测再提示）
             └─ 用户点击"更新" --> [替换中](短暂停后端~1s) --> [已更新, 待重启]
                  └─ 用户点"重启" --> 应用重启 --> 新版本生效
```

> 与既有状态机的差异：将"构建中"（源码通道）替换/并存为"下载中 + 解压中"（产物通道）；空闲/检测/就绪/替换/重启语义不变。源码通道的 `building` 状态保留。

## 4. 功能需求（FR）

> 优先级：P0=核心可用；P1=重要增强；P2=体验优化。

### 4.1 发布侧产物化（FR-RD1）

| 编号 | 需求 | 优先级 | 验收标准 |
|------|------|--------|----------|
| FR-RD1.1 | 发布脚本一键打包 | P0 | `scripts/publish-release.sh <version>`：产出内容 tar.gz + 更新清单，本地冒烟通过 |
| FR-RD1.2 | 产物上传 GitHub Releases | P0 | 脚本（或半自动指引）把 tar.gz 与清单上传到 tag 对应的 Release；同 tag 幂等可覆盖 |
| FR-RD1.3 | 更新清单生成 | P0 | 清单含版本号、tag、tar.gz 下载 URL、sha256、大小、平台；在资产上传成功后生成 |
| FR-RD1.4 | 自动同步上游并发布 | P1 | 上游 `deepseek-ai/deepseek-harness` 发布新 `dsh-v*` tag 后，流水线（GitHub Actions 定时轮询）自动构建产物并发布到本仓库 Releases；重复运行幂等跳过；上游无新版时不产生任何 Release |

### 4.2 检测（FR-RD2）

| 编号 | 需求 | 优先级 | 验收标准 |
|------|------|--------|----------|
| FR-RD2.1 | 触发时机沿用 | P0 | 启动后 20s 首检、每 6h 自动、菜单 ⌘U 手动；与既有调度一致 |
| FR-RD2.2 | 检测源为 GitHub Releases | P0 | 通过 Releases API 或清单文件获取最新 tag，与本地版本对比 |
| FR-RD2.3 | 无新版本静默 | P0 | 版本相同不打扰、不下载 |

### 4.3 后台下载与解压（FR-RD3）

| 编号 | 需求 | 优先级 | 验收标准 |
|------|------|--------|----------|
| FR-RD3.1 | 后台流式下载 | P0 | 下载全程不打断前台；进度可在"关于"面板查看 |
| FR-RD3.2 | 完整性校验 | P0 | 按清单校验大小与 sha256；不符拒绝使用并清理 |
| FR-RD3.3 | 解压到候选区 | P0 | 解压产物验证入口文件与版本号后进入"就绪" |
| FR-RD3.4 | 失败可重试 | P0 | 断网/损坏/磁盘不足均清理半成品，提示可重试，旧版不受影响 |

### 4.4 就绪提示与替换（FR-RD4）

| 编号 | 需求 | 优先级 | 验收标准 |
|------|------|--------|----------|
| FR-RD4.1 | 就绪提示条 | P0 | 复用既有右下角非模态浮条："新版本 vX 已就绪" [立即更新] [忽略] |
| FR-RD4.2 | 原子替换 + 回滚 | P0 | 复用既有 swap/rollback；替换失败自动回滚，应用可用 |
| FR-RD4.3 | 重启生效 | P0 | 替换后弹窗提示重启；重启后新版本生效 |

### 4.5 通道选择（FR-RD5）

| 编号 | 需求 | 优先级 | 验收标准 |
|------|------|--------|----------|
| FR-RD5.1 | 通道设置 | P1 | `settings.json` 新增 `updateSource: release \| source`，默认 `release` |
| FR-RD5.2 | 源码通道保留 | P0 | 切到 `source` 后按既有 git 构建逻辑升级（回归不破坏） |

### 4.6 兼容既有功能（FR-RD6）

| 编号 | 需求 | 优先级 | 验收标准 |
|------|------|--------|----------|
| FR-RD6.1 | 首版内置解包不回归 | P0 | 全新机器首次打开仍解包内置版直接可用 |
| FR-RD6.2 | 既有功能回归 | P0 | 菜单、⌘U、重启后端、关于、日志、优雅退出、冒烟测试通过 |
| FR-RD6.3 | 数据隔离 | P0 | 升级不触碰 `~/.dsh`（sessions/storages/profiles） |

### 4.7 多架构与跨平台预留（FR-RD7）

> 本期只发布 macOS x64 单产物，但**协议层必须按多架构、跨平台设计**（技术文档 §13），后续加平台时设备端与协议零改动。

| 编号 | 需求 | 优先级 | 验收标准 |
|------|------|--------|----------|
| FR-RD7.1 | 清单协议多平台化 | P1 | `latest.json` 含 `schemaVersion`，`assets[]` 按 `os+arch` 可多条目；新增字段只增不减，旧壳兼容 |
| FR-RD7.2 | 产物命名规范 | P1 | `DeepSeek-Harness-<version>-<os>-<arch>.tar.gz`，同一 Release 可并存多平台资产 |
| FR-RD7.3 | 设备端匹配 | P1 | 按本机 `platform+arch` 精确选择资产；无匹配提示"暂不支持本平台/架构"而非报错（用伪造多资产清单单测验证） |
| FR-RD7.4 | 构建矩阵预留 | P2 | 自动发布流水线支持 os × arch 矩阵扩展（§13.3）；本期可只跑 darwin-x64 单一 combo |

## 5. 验收标准

1. 全新机器（删除 `~/dsh-app`）：首次打开 → 解包内置版 → 直接可用（**无回归**）。
2. 发布者打新 tag 并上传产物到 GitHub Releases：设备后台自动检测 → 下载 → 校验 → 解压 → 出现"新版本 vX 已就绪"提示条，期间 GUI 全程可用。
3. 点击"更新"→ 短暂停后端 → 提示重启 → 重启后为新版本。
4. 模拟断网 / sha256 不符 / 产物损坏 / 磁盘不足：清理半成品，提示可重试，旧版本可用，无崩溃。
5. 模拟替换失败：自动回滚，应用可用。
6. 设置切回 `source` 通道：仍可按既有源码构建逻辑完成升级（回归）。
7. 既有功能回归：⌘U、重启后端、关于面板（含下载进度）、升级提示条、优雅退出、冒烟测试。
8. **多架构/跨平台协议预留（FR-RD7）**：伪造含 darwin-x64/darwin-arm64/win32-x64/linux-x64 多资产的清单，设备端正确匹配本机条目；无匹配时提示而非报错；旧版壳读取含新字段的清单不异常。

## 6. 决策记录（已确认 2026-08-20）

| 决策点 | 结论（已确认） | 说明 |
|--------|--------------|------|
| 发布载体 | **GitHub Releases** | 单文件上限 2GB；全量 tar.gz 预计 400–500MB，可行。repo 可通过配置指定（默认与既有 `remote` 一致） |
| 清单格式 | **自研 `latest.json`**（版本/URL/sha256/大小/平台） | 字段可控、不绑定 electron-updater；`latest-mac.yml` 作为备选 |
| 默认通道 | **`release`（产物下载）**，源码构建保留可切换 | 兼顾两者：默认最省事，追新可切回 |
| 候选区目录 | 复用 `harness-new` 语义（下载+解压产物 → 就绪 → 原子替换） | 替换/回滚/状态机基础设施零改动复用 |
| 体积策略 | 全量 tar.gz（与内置 bundle 同源） | 差分/增量更新留后续版本优化 |
| 签名与公证 | 个人自用不签名（沿用） | 分发扩大后另立专项 |
| 多架构/跨平台策略 | **协议先行、构建矩阵后续**：本期只发布 darwin-x64，但清单（schemaVersion/os）、命名、设备端匹配按多平台实现 | 后续加 Windows/Linux/arm64 时协议与设备端零改动（FR-RD7 / 技术文档 §13） |

## 7. 风险与对策

| 风险 | 影响 | 对策 |
|------|------|------|
| GitHub 单文件 2GB 上限 | 产物超限无法上传 | 控制 bundle 体积（裁剪 node_modules / prod-only 打包）；或拆多资产 + 清单聚合 |
| 全量下载体积（500MB–1GB/次） | 升级下载耗时 | 后台下载 + 进度可查（关于面板）；差分更新留后续 |
| 清单与产物不一致窗口 | 设备拿到错误 URL/哈希 | 发布脚本顺序保证：先传资产、后传清单；清单含 sha256 双重校验 |
| 下载中断/损坏 | 半成品占用磁盘 | 临时文件 `.part` 命名 + 启动清理；校验失败即清理重试 |
| 发布纪律 | 忘传产物 → 设备永远等不到更新 | 发布脚本一键化（tag → 打包 → 冒烟 → 清单 → 上传），清单版本驱动；自动流水线（FR-RD1.4）上线后由云端定时兜底 |
| 私仓鉴权（如 repo 为私有） | 设备无法匿名下载 | 支持清单 URL 指向公开 raw；私有场景提供 token 配置（P2，本期不实现则文档注明） |
| 上游发版到产物就绪有时延 | 设备升级晚于上游发版（最长一个轮询周期） | 自动流水线 cron 轮询（默认 6h，可调低）；`workflow_dispatch` 手动立即触发 |
| 多平台构建矩阵成本（后续） | runner 用量翻倍 | 公开仓库免费额度内可控；失败 combo 单独重跑不阻塞其他平台 |
| 原生依赖跨架构（后续） | arm64 产物含 x64 二进制则无法运行 | 在对应架构 runner 上构建打包（§13.3），杜绝交叉编译错配 |
